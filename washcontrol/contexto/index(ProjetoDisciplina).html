1 INTRODUÇÃO

1.1 Contexto de Negócio

O mercado de cuidados automotivos — popularmente chamado de detailing — tem crescido expressivamente no Brasil. As pessoas investem cada vez mais em seus veículos e buscam serviços de qualidade. No entanto, a maioria dos estabelecimentos de pequeno e médio porte ainda opera de forma desorganizada: filas sem controle, anotações em papel, comunicação dispersa via aplicativos de mensagem e ausência de visibilidade financeira.

O WashControl é um sistema Software as a Service (SaaS) multi-tenant desenvolvido para atender lava-cars e estéticas automotivas. Cada estabelecimento cadastrado na plataforma é tratado como um tenant isolado, com seus próprios clientes, veículos, funcionários, ordens de serviço e dados financeiros. A plataforma é administrada centralmente por um Super Admin, que gerencia os tenants, planos de assinatura e faturamento.

A arquitetura multi-tenant permite que o WashControl atenda simultaneamente dezenas de estabelecimentos com um único sistema, reduzindo custos de infraestrutura e facilitando a escalabilidade do produto.

1.2 Justificativa do Projeto

O principal problema que o WashControl resolve é a falta de previsibilidade e controle nos lava-cars. Quando um cliente deixa o veículo e recebe a informação "volta em 2 horas", mas ao retornar o serviço nem foi iniciado, a confiança é destruída. Da mesma forma, o dono do estabelecimento frequentemente não sabe com precisão quanto lucrou no dia, quais funcionários são mais produtivos ou quais insumos estão em falta.

O projeto se justifica pela necessidade de automatizar o fluxo operacional — desde o agendamento até a entrega do veículo — e fornecer visibilidade financeira em tempo real ao gestor. Estabelecimentos que utilizam sistemas organizados passam mais credibilidade ao cliente, conseguem atender maior volume de serviços sem perda de qualidade e tomam decisões baseadas em dados concretos.

1.3 Benefícios

Para o dono do negócio (Manager):

  • Controle financeiro real com Demonstrativo de Resultado do Exercício (DRE) automático;
  • Visibilidade da produtividade da equipe com cálculo automático de comissões;
  • Gestão de estoque integrada ao fluxo de atendimento;
  • Programa de fidelidade configurável para reter clientes.

Para o lavador (Washer):

  • Interface simplificada e responsiva para uso no pátio via celular;
  • Fila de serviços organizada, eliminando conflitos de atribuição.

Para a operação como um todo:

  • Redução de erros humanos (dupla marcação, serviços não cobrados);
  • Rastreabilidade completa do ciclo de vida de cada ordem de serviço;
  • Isolamento total de dados entre estabelecimentos (multi-tenancy seguro).

3.3 Especificações de Casos de Uso

As especificações a seguir detalham os três casos de uso mais representativos do WashControl, cobrindo o fluxo de criação de uma Ordem de Serviço (UC-01), a atualização de seu status ao longo do ciclo de vida (UC-03) e o processo de agendamento prévio de atendimento (UC-11).

3.3.1 UC-01 — Criar Ordem de Serviço

UC-01 — Criar Ordem de Serviço
Breve Descrição

Permite que o Manager registre a entrada de um veículo no sistema, criando uma Ordem de Serviço vinculada a um cliente, um veículo e contendo os itens de serviço e/ou insumos a serem executados. A OS é criada com status PENDING e passa a compor o board Kanban.

Ator Principal

Manager

Ator Secundário

Sistema — valida dados, persiste registros, verifica fidelidade.

Pré-condições
  • O Manager deve estar autenticado com papel MANAGER;
  • O cliente deve estar cadastrado no sistema (ou ser cadastrado durante o fluxo);
  • O veículo deve estar vinculado ao cliente;
  • Deve haver pelo menos um produto/serviço no catálogo do tenant.
Pós-condições
  • Uma nova OS é criada com status PENDING no banco de dados;
  • A OS aparece na coluna PENDING do board Kanban;
  • Os itens (OrderItems) estão vinculados à OS com preços e quantidades.
Fluxo de Eventos
Fluxo Básico

1. O Manager acessa o módulo de Ordens de Serviço.

2. O Manager clica em "Nova OS".

3. O sistema exibe o formulário com campos: cliente, veículo, itens, observações e pagamento antecipado.

4. O Manager seleciona o cliente pelo nome ou telefone.

5. O sistema lista os veículos vinculados ao cliente selecionado.

6. O Manager seleciona o veículo a ser atendido.

7. O Manager adiciona os itens da OS (serviços e/ou insumos) com quantidades e preços unitários.

8. O sistema calcula e exibe o valor total em tempo real.

9. O Manager confirma a criação clicando em "Criar OS".

10. O sistema persiste a OS com status PENDING e redireciona para o board Kanban.

11. O sistema verifica se o cliente atingiu o intervalo de fidelidade e, se aplicável, sinaliza desconto.

Fluxo Alternativo — Cliente não cadastrado

4a. O Manager não encontra o cliente na busca.

4b. O Manager clica em "Novo Cliente".

4c. O sistema exibe o formulário de cadastro de cliente (nome, telefone, e-mail).

4d. O Manager preenche, confirma o cadastro e o fluxo retorna ao passo 5.

Fluxo Alternativo — Criação via Agendamento

1a. O Manager converte um agendamento existente em OS (UC-12).

1b. O sistema preenche automaticamente cliente e veículo a partir do agendamento.

1c. O fluxo continua a partir do passo 7.

Restrição: o sistema bloqueia a criação de segunda OS para o mesmo agendamento (idempotência via Appointment.orderId @unique).

Fluxo de Exceção — OS sem itens

9a. O Manager tenta confirmar a OS sem nenhum item adicionado.

9b. O sistema exibe: "A OS deve conter pelo menos um serviço ou insumo".

9c. O fluxo retorna ao passo 7.

3.3.2 UC-03 — Atualizar Status da Ordem de Serviço

UC-03 — Atualizar Status da Ordem de Serviço
Breve Descrição

Permite que o Manager ou o Washer movam a OS entre os estados do ciclo de vida (PENDING → WAITING_QUEUE → IN_PROGRESS → READY → COMPLETED). Ao atingir COMPLETED, o sistema executa automaticamente os processos financeiro, de estoque e de fidelidade.

Ator Principal

Manager (todos os status)  |  Washer (IN_PROGRESS e READY)

Ator Secundário

Sistema — registros financeiros e de estoque automáticos.

Pré-condições
  • O usuário deve estar autenticado;
  • A OS deve existir e pertencer ao tenant do usuário;
  • A transição de status deve ser válida conforme o ciclo de vida definido.
Pós-condições
  • O status da OS é atualizado no banco de dados;
  • Os timestamps correspondentes são registrados (startedAt, finishedAt, completedAt);
  • Se COMPLETED: FinancialTransaction, InventoryTransaction, totalWashes++ e comissão são gerados automaticamente;
  • A interface é atualizada em no máximo 2 segundos (RNF03).
Fluxo de Eventos
Fluxo Básico — Conclusão de OS (READY → COMPLETED)

1. O Manager localiza a OS na coluna READY do board Kanban.

2. O Manager clica em "Concluir / Registrar Pagamento".

3. O sistema exibe o formulário de conclusão: método de pagamento, valor total e valor adiantado.

4. O Manager seleciona o método de pagamento (PIX, Dinheiro, Cartão Crédito ou Débito).

5. O Manager clica em "Confirmar Conclusão".

6. O sistema atualiza o status para COMPLETED e registra completedAt = now().

7. O sistema cria automaticamente: FinancialTransaction (INCOME), InventoryTransaction OUT por insumo utilizado e decrementa Product.stock.

8. O sistema incrementa Customer.totalWashes e verifica o programa de fidelidade.

9. O sistema calcula e registra a comissão do Employee vinculado.

10. O card da OS é movido para o histórico de OSs concluídas.

Fluxo Alternativo — Lavador inicia serviço (WAITING_QUEUE → IN_PROGRESS)

1. O Washer acessa a visão do pátio.

2. O Washer clica em "Iniciar" no card do veículo.

3. O sistema atualiza o status para IN_PROGRESS e registra startedAt = now().

4. O card é movido para IN_PROGRESS no Kanban do Manager.

Fluxo Alternativo — Cancelamento

1. O Manager seleciona "Cancelar OS" no menu do card.

2. O sistema solicita confirmação.

3. O sistema atualiza o status para CANCELED.

Restrição: somente MANAGER pode cancelar uma OS (RNF05).

Fluxo de Exceção — Transição inválida

1. O sistema rejeita transições fora do ciclo definido (ex: PENDING → COMPLETED).

2. O sistema exibe mensagem informando os status válidos para transição.

3.3.3 UC-11 — Criar Agendamento

UC-11 — Criar Agendamento
Breve Descrição

Permite que o Manager registre previamente um horário de atendimento para um cliente e veículo, reservando uma vaga na agenda do lava-car. O agendamento permanece com status SCHEDULED até ser convertido em OS ou cancelado.

Ator Principal

Manager

Ator Secundário

Sistema — valida disponibilidade de horário e notifica o cliente.

Pré-condições
  • O Manager deve estar autenticado com papel MANAGER;
  • O cliente e veículo devem estar cadastrados no sistema;
  • O horário solicitado não deve estar ocupado por outro agendamento.
Pós-condições
  • Um novo Appointment é criado com status SCHEDULED;
  • O agendamento aparece no calendário do sistema;
  • O cliente pode receber uma notificação de confirmação (RF09).
Fluxo de Eventos
Fluxo Básico

1. O Manager acessa o módulo de Agendamentos.

2. O Manager clica em "Novo Agendamento".

3. O sistema exibe o formulário: data/hora, cliente, veículo, serviço desejado e observações.

4. O Manager seleciona a data e horário desejados.

5. O sistema verifica a disponibilidade do horário selecionado.

6. O Manager seleciona o cliente e o veículo.

7. O Manager confirma o agendamento.

8. O sistema persiste o Appointment com status SCHEDULED e exibe no calendário.

Fluxo Alternativo — Conversão em OS

1. No dia do atendimento, o Manager clica em "Converter em OS".

2. O sistema cria uma OS pré-preenchida com os dados do agendamento.

3. O sistema vincula a OS ao agendamento via Appointment.orderId.

4. O status do agendamento é atualizado para COMPLETED.

Fluxo de Exceção — Conflito de horário

5a. O sistema detecta outro agendamento no mesmo horário.

5b. O sistema exibe: "Horário indisponível. Selecione outro horário."

5c. O Manager seleciona horário alternativo e o fluxo retorna ao passo 6.

Fluxo de Exceção — Idempotência (OS já existente)

1a. O Manager tenta converter um agendamento que já possui OS vinculada.

1b. O sistema rejeita a operação com a mensagem: "Este agendamento já possui uma OS vinculada".

1c. O sistema redireciona para a OS existente (Appointment.orderId @unique).

7 CRIATIVIDADE

Os itens abaixo foram identificados pela equipe como contribuições criativas — itens não solicitados explicitamente pelo enunciado que tornam o trabalho superior em relação ao mínimo esperado. O item de criatividade pode relacionar-se ao projeto (documento) e ao produto que está sendo gerado.

7.1 Criatividade no Projeto (Documento)

C01 — Protótipo de alta fidelidade funcional Em vez de um protótipo estático no Figma, o WashControl foi desenvolvido como aplicação funcional em Next.js 15 com banco de dados real (PostgreSQL), autenticação e Server Actions — tornando o protótipo interativo, demonstrável e com dados reais de teste via seed.
C02 — Técnicas de Elicitação com rastreabilidade completa Cada técnica utilizada (Entrevista, Observação, Questionário, Brainstorming, JAD) foi documentada com stakeholder-alvo, roteiro aplicado, limitações encontradas e mapeamento direto para os RFs/RNFs resultantes — indo além da simples listagem de técnicas exigida.
C03 — Diagrama de Objetos com cenário real e justificativa O diagrama de objetos apresenta uma instância concreta de atendimento em andamento, com valores reais e justificativa explícita das classes representadas e das omitidas — evidenciando compreensão profunda da diferença entre diagrama de classes e diagrama de objetos.
C04 — Idempotência modelada como regra de negócio explícita A restrição Appointment.orderId @unique foi especificada como regra de negócio (RN-03) e representada em fluxos alternativos, fluxos de exceção e no diagrama de estados do Agendamento — demonstrando maturidade na modelagem de restrições de integridade.

7.2 Criatividade no Produto

C05 — Arquitetura multi-tenant com isolamento estrutural por tenantId O isolamento de dados entre estabelecimentos é garantido em nível de banco de dados: o campo tenantId é obrigatório em todas as tabelas, com índice composto para eficiência — não é um isolamento lógico por aplicação, mas arquitetural e auditável.
C06 — Automações em cascata ao concluir OS (5 ações em transação única) Ao marcar uma OS como COMPLETED, cinco ações são executadas atomicamente: (1) receita financeira, (2) baixa de estoque por insumo, (3) contagem de fidelidade, (4) verificação de desconto e (5) cálculo de comissão do funcionário — modelado e implementado.
C07 — Programa de fidelidade parametrizável por tenant Cada lava-car configura seu próprio programa de fidelidade via loyaltyInterval (a cada N lavagens) e loyaltyDiscount (X% de desconto) no modelo Tenant — um diferencial competitivo que vai além dos requisitos documentados.
C08 — Módulo de faturamento SaaS B2B para o Super Admin Além do sistema para o lava-car, existe um módulo de faturamento onde o Super Admin gerencia planos (BASIC, PRO, ENTERPRISE), valores de assinatura e datas de vencimento dos tenants — tornando o WashControl um produto SaaS completo, não apenas um sistema de gestão isolado.
